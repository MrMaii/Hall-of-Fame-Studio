# Agent Consciousness Architecture

This folder owns the app-facing agent runtime. It is intentionally model-agnostic: today it produces deterministic behavior for the React prototype, and later the same protocol can wrap BYOK LLM calls.

## Core Idea

An Agent is not only a prompt. In this product, an Agent is a working node with five layers:

1. **Identity**: name, role, persona skill, capability lanes.
2. **Mind**: current goal, open obligations, working memory, confidence, attention policy.
3. **Relations**: lead, reviewer, manager, managed peers, lateral peers.
4. **Communication Policy**: when to read, when to stay silent, when to respond, when to escalate.
5. **Work Cycle**: hourly private work pulses and daily public reports.

The Director does not continuously drive the team. The Director starts or changes intent; the Agent network then works through its own communication loop.

## Lead Mode

Every project starts with one Lead. The Lead is selected by task fit plus management score.

The Lead does not micromanage every sentence. The Lead owns:

- agenda and decision framing
- owner/deadline assignment
- cross-agent dependency resolution
- deciding whether an issue needs Director input
- maintaining the project ledger

The Reviewer is selected separately. The Reviewer can challenge the Lead and force evidence or verification before a decision becomes durable.

The default relationship graph is:

- Lead coordinates all non-lead Agents.
- Reviewer reviews the Lead.
- Every Agent can read peers directly.
- Agents only escalate to the Director when a decision changes scope, budget, deadline, acceptance criteria, or risk tolerance.

## Meeting Speech Frames

Agents do not improvise randomly in meetings. Each meeting type gives every participant a required speech frame.

### Kickoff

Lead says:

- goal
- scope
- owners
- first-cycle deadline
- decision log

Each Agent says:

- role
- first artifact
- dependency
- risk
- deadline

The output is a project charter. In the runtime this is stored as `kickoffCharter`, including the approved meeting result, confirmed Leader, Reviewer, team roster, next actions, communication rules, and evidence ids for role negotiation, Leader campaigns, and assignments.
The charter also stores hearing edges for role negotiation and Leader campaigns, so the system can prove that Agent turns were visible to peers rather than isolated one-on-one responses.

### Recurring Sync

Lead says:

- progress map
- blockers
- deadline pressure
- decision queue

Each Agent says:

- done
- doing
- blocked-by
- next-delivery
- confidence

The output is a status ledger.

### Review

Lead says:

- review target
- acceptance bar
- open risks
- owner fixes

Each Agent says:

- finding
- evidence
- severity
- fix owner
- verification

The output is a review verdict.

### Working Discussion

This is the non-ceremonial work channel.

Lead says:

- current objective
- coordination need
- handoff point

Each Agent says:

- signal
- interpretation
- action
- request

The output is work notes or a handoff.

## Work Communication Logic

Agents themselves do not "call meetings" during normal work. They communicate inside the work stream.

For every message, each Agent runs a read pass:

1. Is this a direct mention?
2. Is this from the Lead?
3. Is this from someone I manage?
4. Does this match my capability lane?
5. Does it contain a blocker, handoff, decision, risk, or deadline?

The runtime converts that into an attention score.

- Below 45: ignore for now.
- 45-71: read silently and update working memory.
- 72+: speak if the Agent can improve the plan.
- Direct mention: always speak unless the message is only FYI.

The speaking Agent must produce one of:

- acknowledgement
- correction
- handoff
- blocker report
- evidence request
- deadline negotiation
- decision proposal

This avoids noisy "everyone comments on everything" behavior.

## Long-Running Work

A station can run without user interference by scheduling work cycles.

### Autonomous Run Control

The backend exposes `GET /projects/:id/autonomous-run-control` as `autonomous-run-control/v1`. It also exposes `POST /projects/:id/autonomous-run-control/:actionId/run` for executing a listed next action through the delegated queue/scheduler lane, `POST /projects/:id/autonomous-run-control/run-loop` for a bounded loop over that same surface, `GET|POST /projects/:id/autonomous-run-control/sessions...` for the project-scoped Autopilot session layer, and `POST /workers/autopilot/due` for opt-in scheduler advancement of active bounded sessions.

This read model is the Manager-facing control surface for unattended work. It summarizes:

- the next Manager orchestration action
- the next Agent-selected autonomous action
- the backend scheduler tick route
- queued project/Agent/Autopilot session worker rows
- proof ids, timeline ids, and event ids
- gates that distinguish local/private-pilot autonomy from production autonomy

Manager Dashboard embeds the light control view. Manager Ready Package embeds the worker-queue-backed view. Manager Flow Graph renders it as an execution node, and Readiness Proof Map exposes its proof route. Run receipts use `autonomous-run-control-action-run/v1`, persist into project logs, `autonomousRunControlRunLedger`, and the event ledger, then surface as Dashboard rows, Flow Graph receipt nodes, Proof Map routes, and the delegated Agent's own Dashboard. Direct action responses also expose delegated output objects so React can render `Run Control Output Nodes` for submissions, evidence searches, reviews, review responses, artifacts, or result-message proof immediately under the run receipt. Loop receipts use `autonomous-run-control-loop-run/v1`, persist into `autonomousRunControlLoopLedger`, record each step receipt plus a stop reason, and surface in Manager Dashboard, Manager Ready Package, Manager Flow Graph, and Readiness Proof Map. Autopilot sessions use `autonomous-run-control-session/v1`; explicit ticks and due-worker ticks use `autonomous-run-control-session-tick/v1`, persist into `autonomousRunControlSessionLedger` and `autonomousRunControlSessionTickLedger`, link back to child loop/run receipts, carry the participating Agent ids, task ids, action ids, and action lanes, and attach an `autopilot-delivery-target/v1` snapshot of Product Team Delivery Trace progress. Before each tick runs, the next missing trace stage is translated into `autopilot-delivery-target-control/v1`; that target control is injected into delegated Agent/Manager/scheduler request bodies as the concrete artifact, evidence-search, review, or revision intent, and each loop step records `autonomous-run-control-target-selection/v1` candidate scores for Manager, Agent, or scheduler lanes. Worker Queue Snapshot exposes active sessions as `autopilot-session` rows with idempotency, lease, direct tick, and `/workers/autopilot/due` route contracts, while HTTP scheduler status records `scheduler-autopilot-controls/v1` and Autopilot counters when enabled. Completed session ticks now also export worker execution receipts with `sessionId`, direct tick recovery routes, and `worker_runs` persistence rows; the file-backed backend can reload a running session after restart and resume it through the due-worker; queue adapter plan/dry-run, Operations Readiness metrics, and the private adapter gateway import, lease, dispatch, acknowledge, and parity-check this Autopilot lane alongside project and Agent workers. Operations Readiness also checks the provider side of autonomous work: provider usage ledger rows, provider eval receipts, source snapshots, provider receipts, event proof, persistence counts, and the secret-vault boundary now appear in the recovery gate, alert rules, runbook, and incident drill before autonomous model/search calls resume. Action, loop, session start/tick/pause, and due-worker writes now return a dedicated `readModels` contract when `includeReadModels: false`: sessions, active tick/pause, scheduler tick, Autopilot due-worker, Agent queue, Product Team Operating Loop, Autonomous Cycle Consistency, Flow Graph, Proof Map, timeline, events, and transcripts all have explicit refresh routes. React Backend Worker Station consumes those routes through `refreshAutonomousRunControlReadModels` after Autopilot commands. The scheduler-owned route remains the primary Autopilot continuation path: `Scheduler Tick` calls `/workers/autonomous/tick` with Autopilot enabled, stores the returned worker receipt, and shows the due-worker path; direct session tick remains as an explicit manual fallback. This makes a C-side run button, bounded loop, bounded session, or controlled scheduler tick auditable from the A-side Agent workspace as well as the Manager aggregate, while keeping each autonomous tick tied to the next generic delivery gap instead of a research-specific script.

Agent initiative is part of that audit path. Agent worker queue rows carry the same `agent-autonomous-initiative/v1` projection used by Agent Autonomous Action Queue and Product Team Operating Loop, including `agentInitiativeId`, target artifact type, strategy intent, and run route. Run/loop receipts freeze the executed initiative when an Agent lane runs; session tick receipts freeze the candidate Agent initiative ids and artifact targets visible before lane selection.

Product Team Mission Runner handoff is now part of that same operating-loop audit. `product-team-customer-agent-handoff/v1` records the C-side approved roster, Leader, Reviewer, target stage, and A-side session/tick route. Product Team Operating Loop derives `product-team-customer-agent-handoff-execution/v1` from the persisted Autopilot session, tick receipts, loop/action run receipts, result message ids, and Agent submissions. The Manager can therefore see whether a customer-approved mission has only started an A-side session, has recorded the first tick, or has produced run receipts/output submissions, and the Flow Graph/Collaboration Intent Queue use the same backend summary instead of a frontend-only button state.

### Event Ledger Replay Recovery

The runtime keeps `eventLedger` as an append-only, sequence-numbered proof stream with a bounded retained window. The local retained limit is `EVENT_LEDGER_RETAINED_LIMIT = 5000`; the summary still reports both retained and total event counts so a Manager can see whether the stream has been pruned.

Long-running Agent work must not lose manager readiness simply because early kickoff events have aged out of the retained window. `projectEventReplayProjection` can rebuild the core replay coverage from durable project records, including `kickoffCharter`, `changeLedger`, `peerHandoffs`, and `autonomousSchedulerLedger`, while preserving the retained ledger's contiguous sequence window. `backfillProjectEventLedger` still uses the retained projection when it needs to migrate legacy projects, so the recovery path does not hide missing retained events during migration. This is the local/private-pilot recovery contract; production still requires managed immutable audit storage and retention controls.

### Hourly Cycle

Each Agent privately does:

- inspect new messages
- update obligations
- advance the current artifact
- detect blockers
- publish only if something changed

Hourly public frame:

- last observable change
- current task
- blocked signal
- next hour

### Daily Cycle

Each Agent produces a more durable report:

- completed
- planned
- deadline
- risks
- requests

The Lead consolidates daily reports into the project ledger. The Reviewer attaches verification notes when the work touches evidence, quality, risk, security, or acceptance criteria.

The runtime supports this through two layers:

- `planAutonomousWorkCycle`: computes what every Agent should read, work on, publish, or keep private.
- `evaluateAutonomousSchedule`: decides whether an enabled project is due to run, why it is due or waiting, and what the next scheduled time is.
- `advanceAutonomousProjectCycle`: turns that cycle into a project-state update with logs, task touches, task-completion events, progress movement, scheduler evidence, `lastAutonomousRunAt`, and `nextAutonomousRunAt`.
- `publishAutonomousCycleChat`: publishes the visible autonomous cycle messages into group chat semantics, delivering direct management mentions into Agent inboxes/worklogs and appending `group-chat-message` entries to the unified event ledger.

In the local backend, the HTTP server can run the same hourly/daily worker loop on an interval. A production backend can replace the interval runner with a queue or cron process while keeping the same due-worker contract, then optionally call the configured BYOK model provider only for Agent plans that actually need generation.

### Backend Service Boundary

`agentProjectService.js` is the backend-oriented facade over the pure runtime. It is intentionally independent from React and localStorage so an API route, queue worker, or local prototype can call the same contract:

- `createAgentProjectService`: wraps a project repository and exposes backend-style commands for tests, prototype workers, and future API routes.
- `createAgentProjectMemoryStore`: the in-memory repository adapter for tests and browser-adjacent prototypes. It stores hydrated project snapshots, retained project messages, durable kickoff meeting sessions, backend security audit-stream records, and signed access replay records, exposes `saveProject`, `saveKickoffMeeting`, `appendMessages`, `getMessages`, `appendSecurityAuditRecords`, `listSecurityAuditRecords`, `appendAccessReplayRecords`, `listAccessReplayRecords`, and `snapshot`, and can be replaced by another adapter with the same shape.
- `createAgentProjectFileStore`: the Node-backed repository adapter. It persists the same project/message/kickoff-meeting/security-audit-stream/access-replay snapshot to JSON on disk, mirrors security access decisions into an append-only JSONL audit sink, reloads the snapshot, replay records, and audit sink on service restart, and proves the backend command facade can survive process boundaries before a database adapter exists. Security audit-stream rows carry project-local `previousStreamHash` / `streamHash` links so the read model can detect missing, broken, or mismatched local audit chains.
- Store migrations are explicit local transactions rather than an in-memory version bump. Each registered edge owns up/down/validate behavior; exact source bytes are archived outside rotating backup state; a checksummed prepared/committed journal survives both migration crash windows; the target is reread and semantically verified. `scripts/rollback-agent-project-store-migration.mjs` is dry-run by default and requires `--execute --migration-id` to apply a verified offline down migration while preserving a pre-rollback archive and post-migration business data.
- Local artifact storage treats `.versions/<sha256>` as canonical and workspace files as mutable projections. Canonical creation is atomic and existing content is reverified before reuse. A content-minimized JSONL hash chain records references, retention, legal holds, and releases; `/projects/:id/local-artifact-storage` rereads every canonical checksum, separates projection drift from canonical corruption, exposes expiry without deleting, and survives restart. Legal-hold writes use the authorized local user identity; capability 13 remains responsible for approved lifecycle deletion.
- `npm run agents:local-privacy-lifecycle` verifies capability 13's pure-local retention executor. Project privacy policy supplies bounded artifact retention days and automatic-review scan mode. `GET /projects/:id/privacy/lifecycle` previews without mutation; security-admin scan persists an exact one-hour plan; execution requires `execute=true`, the exact plan checksum, an operation id, and a critical approval from distinct Manager and security-admin users. A prepared journal survives the post-delete crash window, canonical/internal projections are checksum-verified before removal, the external workspace is never deleted, the artifact ledger records deletion, and an outside-project tombstone lists residual backup/recovery/audit boundaries. This is local lifecycle governance, not remote deletion or public-production compliance evidence.

## Collaboration Invariants

The system should preserve these rules:

- No ownerless task.
- No decision without a recorded reason.
- No blocker without an owner.
- No deadline change without Lead visibility.
- No risk acceptance without Reviewer visibility.
- No Director interruption unless the team cannot decide inside its authority.

The runtime exposes `evaluateCollaborationState` to check these rules against the current project. The dashboard renders the resulting collaboration health score and each failed check so broken coordination is visible before it becomes silent drift.
