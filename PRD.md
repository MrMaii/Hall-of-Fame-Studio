# AI 虚拟项目组平台产品需求文档（PRD）最终定稿版

## 一、文档概述

### 1.1 项目名称

**AI Virtual Team** —— 全 AI 驱动虚拟项目组协作平台

### 1.2 核心定位

一款开源可私有化部署、采用 **BYOK（By Your Own Key）** 自研 API 密钥运行模式的 AI 协作工具，核心为用户打造纯 AI 雇员组成的虚拟项目组，实现从项目立项、分工、执行到进度追踪、迭代修改的全流程 AI 自主化协作，所有 AI 雇员具备独立思考、主动讨论、自主工作能力。

### 1.3 技术模式

- 开源免费，支持用户本地 / 服务器私有化部署
- 无平台内置 API 服务，采用 BYOK 模式：用户填写自有大模型 API 密钥即可运行
- 所有数据、对话、项目记录本地存储，无云端上传，保障用户隐私

### 1.4 文档说明

本 PRD 仅描述产品功能、交互流程、核心规则，不绑定任何具体现实人物，AI 雇员以领域能力标签做差异化区分，所有案例均为功能场景说明。

### 1.5 验证场景说明

本产品定位为通用的 AI 产品团队协作系统，不为某一个垂直场景单独定制。Research Project 可作为早期验收样例，因为它同时包含需求澄清、信息搜集、证据判断、头脑风暴、写作、评审、群聊协作、节点提交和最终交付等典型产品团队能力。

因此，Research Project 的作用是测试系统能否完整跑通一个复杂产品工作流，而不是把产品限定为论文写作或研究工具。

该验收样例必须覆盖通用产品团队的核心闭环：Agent 主动搜集信息并形成证据记录，基于证据提交阶段性产物，Reviewer 对产物提出修改意见或确认通过，修改后的产物继续进入最终交付。上述动作都应进入项目记录、群聊、流程图和可追溯证明链，而不是只停留在聊天文本中。

产品必须区分三种就绪状态：一是通用产品团队闭环是否已经达到本地内测 / MVP 演示标准，二是系统是否可以进入受控私有试点，三是系统是否已经满足正式生产上线要求。MVP 就绪可以基于会议治理、角色自荐、脑暴、证据判断、提交、评审、修订、最终交付、后端 worker 和证明链路来判断；私有试点上线包必须聚合这些证据并给出 private-pilot go/no-go；私有试点真正放行还必须经过 Manager 与 security-admin 的上线审批记录；生产上线仍必须单独显示密钥保管、权限、安全边界、托管持久化、数据库迁移计划与 dry-run 验证、数据库 adapter cutover 验证、队列调度、真实 provider、监控恢复、operations-owner 生产审批等阻塞项。

MVP readiness must be an operator-facing scheduling contract, not only a score table. `GET /projects/:id/mvp-readiness` must expose `nextShortestPath` and `operatorActions` with scope, owner, method, `apiPath` / `runApiPath`, status, and production-blocker flags. When the core local MVP is incomplete, the next action must point to the missing core route and, when the gap can be advanced by the Agent/worker side, include an `autopilot-delivery-target-control/v1` target with the next generic product-team stage. The draft/review/revision/final-deliverable gaps must be step-sensitive: the system should target product brief creation, requested-changes review, linked revision response, final deliverable submission, and final acceptance according to what evidence is currently missing. Once the generic product-team loop is closed, the model must point to private-pilot handoff and production-hardening routes while keeping `readyForProduction: false`. `POST /projects/:id/mvp-readiness/operator-actions/:actionId/run` must record a lightweight `mvp-readiness-operator-action-run/v1` receipt with timeline, event-ledger, Flow Graph, and Proof Map proof; runnable core-gap receipts must enter Collaboration Intent Queue and Autonomous Run Control as a target handoff, and running that handoff must produce the requested Agent submission/review node with chat/timeline/event/workspace proof. If an operator action, Agent Autonomous Action Queue row, or Collaboration Intent Queue row fails, the Manager UI must show the failed attempt and clear stale prior receipts/output instead of displaying an earlier successful run as proof for the current click. Production-hardening receipts must remain non-autonomous and must not claim the target production blocker is closed. The Manager UI must render and record those actions from the backend contract rather than inventing local launch guidance.

The product must also provide a general Mission Runner contract for starting a real product-team project from a customer goal without building a research-only shortcut. `POST /product-team-missions` must create and approve the kickoff meeting or reuse the customer-approved kickoff meeting, preserve Leader/Reviewer/next-action decisions, start a bounded Autopilot session, optionally run the first A-side tick, and persist `product-team-mission-run/v1`. The receipt must include `product-team-customer-agent-handoff/v1`, freezing the Manager-approved team, Leader, Reviewer, A-side Autopilot session/tick status, target delivery stage, and next backend routes into Product Team Delivery Trace, Operating Loop, Collaboration Intent Queue, and Autonomous Run Control. The Product Team Operating Loop must expose that handoff under `customerSide.handoff`, and Collaboration Intent Queue must project it as a runnable `product-team-customer-agent-handoff` row so the C-side approval can visibly continue into A-side execution. The Manager-facing initiation approval must use this route for real backend projects so project creation, meeting approval, and A-side autonomy startup are one auditable C/A contract. That receipt must appear in Manager Dashboard, Manager Flow Graph, Readiness Proof Map, timeline/event proof, and `GET /projects/:id/product-team-missions`, with routes to transcripts, Product Team Delivery Trace, Product Team Operating Loop, Collaboration Intent Queue, and Autonomous Run Control. Manager UI must also show a compact backend-sourced Planner / Executor / Reviewer state panel so a non-technical operator can see whether responsibility moved from kickoff planning to artifact execution to review/revision/final acceptance without reading raw JSON. This contract may prove local/private-MVP mission startup; it must keep `readyForProduction: false` until managed identity, BYOK/provider policy, queue/cron, persistence, audit, cost controls, and recovery are complete.

The real-user acceptance path must be evaluated as an end-to-end product experience, not as isolated API success. A fresh user must be able to open Settings, type provider values, seal them through the backend Secret Vault, start a generic product-team mission from the workspace, approve kickoff, run the C/A handoff, then see an Agent continue independently through Agent Autonomous Action Queue into a substantive submission with action-decision, chat, timeline, event, and Flow/Proof traceability. The user must also inspect the resulting Artifact Quality Audit, Product Team Delivery Trace, Submission Review Workflow, Evidence Index readiness, Proof Map routes, and Flow Graph final-deliverable node in Manager UI. Passing this path may prove local/private-MVP usability, but it must not be treated as public production readiness while managed identity, production BYOK/KMS, durable persistence, managed queue/cron, centralized observability, cost controls, and incident recovery remain open.

The Manager Dashboard must expose the C/A handoff as a backend-backed first-run action even before the full Manager Ready Package has synced. If the standalone `collaboration-intent-queue/v1` route is available, the UI must render the Mission Handoff row, prioritize `customer-agent-handoff-intent`, run it through `POST /projects/:id/collaboration-intent-queue/:intentId/run`, display returned delegated Agent Submission output nodes, and provide chat/timeline proof exits without creating local snapshot proof.

## 二、核心用户完整使用流程

### 2.1 第一步：创建虚拟项目组

1. 用户进入平台，点击新建项目组
2. 自定义填写项目组名称，可补充项目简介（非必填）
3. 项目组创建完成，进入项目组专属控制台

### 2.2 第二步：AI 雇员市场招聘

1. 从项目组控制台进入雇员招聘市场
2. 市场按专业能力领域分类展示 AI 雇员（如商业管理、产品设计、技术研发、视觉设计、品牌内容、项目统筹等）
3. 每个 AI 雇员展示：独立人设标签、核心擅长领域、专业能力描述、独立行事风格
4. 用户自主选择、一键雇佣 AI 雇员，已雇佣雇员自动纳入当前项目组员工列表
5. 支持随时返回市场增聘、解聘 AI 雇员

### 2.3 第三步：召开项目立项会议（核心流程）

#### 2.3.1 会议启动

用户发起第一次项目立项会议，默认全员参会，支持手动勾选参会 AI 雇员。

#### 2.3.2 会议形式

采用圆桌会议可视化界面，所有参会 AI 雇员以独立角色展示，模拟真实圆桌讨论场景。

#### 2.3.3 立项会议完整流程

**需求确认环节**

- AI 雇员主动向用户发起提问，集体确认项目核心目标：明确要做的产品 / 项目核心定位、核心诉求
- 各 AI 雇员按领域，轮流提出抽象化产品问题，进一步细化需求（如目标受众、核心价值、落地方向、边界范围等）
- 用户逐一回复解答，直至 AI 雇员完全明确项目需求

**分工协商环节**

- 需求确认完毕后，AI 雇员主动向用户询问自身分工安排
- 用户下达分工指令后，AI 雇员基于自身能力，主动提出分工调整意见（如跨领域配合、分工合理性优化、权责补充等）
- 用户最终确认分工方案，所有 AI 雇员达成一致

**立项定稿**

- 会议达成全部共识，项目正式立项
- 系统自动生成本次立项会议核心结论、分工方案，同步存入项目纪要

### 2.4 第四步：AI 自主执行项目工作

1. 立项完成后，进入项目进度专属页面
2. 所有 AI 雇员按照立项会议确定的分工、需求，自主开展工作，无需用户实时指令
3. 进度页实时展示整体项目推进进度、各 AI 雇员工作状态、当前完成节点
4. 系统自动记录每日工作内容，每个 AI 雇员自动生成每日工作汇报，同步至项目日志
5. 项目执行期间，AI 雇员仅在遇到核心决策问题时，主动向用户提问确认
6. AI 雇员可按规范提交阶段性产出，例如研究报告、证据包、决策建议、风险复核、执行计划等，提交后作为流程图节点供用户查看、比较、复核或退回修改
7. AI 雇员可在项目流程中主动表达自身适合承担某项工作的理由，例如角色自荐、Leader 竞选、评审请求、产出提交说明等，该类“自我说明”应作为可追溯协作证据进入流程图或项目记录
8. AI 雇员可提交信息搜集与证据记录，包括搜索问题、来源、证据质量、结论摘要和关联任务，用户可在任务证据、流程图和项目记录中查看
9. Reviewer 可对 Agent 提交的产物进行正式评审，支持“要求修改”和“确认通过”两类基础结果；评审意见、修改要求、最终通过记录都应成为可追溯节点
10. AI 雇员的自主执行应包含可审计的下一步行动判断：系统需要记录每次 Agent worker 为什么选择继续任务、提交产物、审核他人提交、回应修改要求或仅监控项目，并把该判断暴露给 Manager Dashboard、Agent Dashboard、流程图和事件证据链
11. 项目控制台必须提供受限自主运行控制：用户可以单步运行一个后端选择的下一步动作，也可以启动有最大步数限制的自主循环。循环必须记录每一步实际执行的后端 receipt、停止原因、关联 Agent、timeline/event proof 和流程图节点，不得作为无限制后台运行或生产级自动化来宣传
12. The project control surface must support a bounded Autopilot session mode for private-MVP validation: the Manager can start a session with loop/step budgets, advance it by explicit ticks, pause it, and inspect session/tick receipts. Each tick must link to the actual child loop/run receipts, timeline/event proof, Flow Graph nodes, Readiness Proof Map routes, and a generic Product Team Delivery Trace target snapshot showing ready stages, missing stages, and the next missing delivery stage. The tick must translate that missing stage into an auditable target-control intent, inject that intent into the delegated execution request as artifact/evidence/review controls, and record why the selected Manager, Agent, or scheduler lane was chosen. This must not be positioned as literal consciousness or production-grade unattended daemon infrastructure.

### 2.5 第五步：项目迭代修改（会议制修改规则）

1. 项目执行过程中，所有修改、需求调整、方向变更，均需通过召开会议完成
2. 用户可自主选择参会 AI 雇员范围（全员 / 指定人员）
3. **会议流程**：用户提出修改诉求 → AI 雇员讨论反馈 → 确认修改方案 → 执行修改
4. 会议结束后，系统自动总结本次会议核心要点、修改指令、执行要求，展示在项目控制台核心区域，同步更新至项目纪要
5. AI 雇员根据会议结论，自主调整后续工作内容

### 2.6 项目闭环

项目完成后，AI 雇员提交最终成果总结，生成完整项目日志、会议纪要、工作记录，用户可查看、导出全部项目资料。

## 三、核心产品规则

| 规则 | 说明 |
|------|------|
| **AI 雇员独立性** | 所有 AI 雇员为独立思考个体，具备主动讨论、主动提问、提出意见、自主工作的能力，非被动指令执行工具 |
| **修改唯一规则** | 禁止零散对话式修改，所有项目变更必须通过会议形式发起，确保协作流程规范化 |
| **会议纪要留存** | 每一次会议（立项会、迭代会、协调会），系统均自动生成核心总结，永久留存 |
| **工作可追溯** | 项目全流程留痕，包含所有会议记录、AI 每日工作汇报、进度变更记录、分工调整记录，用户可随时查阅 |
| **通用产物节点** | Agent 产出必须以通用产品团队 artifact 类型提交为流程图节点，至少覆盖 discovery-report、brainstorm-board、evidence-packet、product-brief、decision-proposal、risk-review、revision-note、implementation-plan 和 final-deliverable；Research Project 只用于验证这些通用节点，不得形成论文专用协议 |
| **产物提交证明** | 每个 Agent submission 必须带有后端生成的 `agent-artifact-storage-proof/v1`，至少包含写入状态、工作区路径或未来对象存储 URL、正文 checksum、proof checksum 和工作区文件证明；Manager Dashboard、Flow Graph、Proof Map、Artifact Quality Audit、Project Evidence Archive 与 persistence snapshot 必须共用同一份证明，前端不得只凭本地正文把节点渲染为已提交产物 |
| **后端产物草稿生成** | Agent 必须能基于项目上下文、任务、证据搜索、前序提交与评审意见生成 `agent-artifact-draft/v1` 草稿；草稿可被直接提交为标准 Agent submission，并进入流程图、任务证据、群聊、timeline、事件账本、工作区文件和 Proof Map。Manager Dashboard、Agent Dashboard、归档包和持久化迁移行必须保留草稿来源、draft id、checksum、本地/模型生成状态、proof context 与 `artifact-draft-quality/v1` 质量 gate。首版验收必须同时覆盖本地 fallback 生成器和 provider policy 约束下的 deterministic model-backed draft；模型草稿必须标记人工复核要求，并在 Provider Readiness 中显示 model draft quality / human review gate。真实 LLM 生产生成必须走 BYOK/provider policy、校准后的质量审核、限流预算和事故控制 |
| **真实后端读模型刷新** | 真实项目的前端不得在后端在线时用本地 mock 行补齐 Manager Dashboard、Manager Ready Package、Flow Graph 或 Agent Dashboard。Agent 提交、证据搜索、草稿提交，以及立项/kickoff approval、Manager Command Center、Scenario Walkthrough、Action Queue、群聊、会议、变更请求、autonomous cycle、Agent work-cycle、worker due 和 production operations/deployment/security/provider control receipt 等写入动作可先返回轻量后端 receipt，并通过 `includeReadModels: false` 暴露后续应刷新的后端读模型路由；前端必须按这些路由刷新真实投影，而不是静默合成本地数据。Agent Focus Workbench 是首个前端入口：证据、通用产物提交、草稿生成并提交都必须走后端 Agent 路由并形成可追溯节点；若这些写入失败，前端必须显示失败并清除旧成功 receipt 的证明含义，不得把上一次成功提交展示为当前提交已完成；后续 Manager/worker/production-control 控制面也必须逐步迁移到同一 receipt-first 协议 |
| **Private Pilot Operations Readiness** | 私测 acceptance report 之后，Manager Ready Package 和 `GET /projects/:id/production-operations-readiness` 必须暴露同一份 `production-operations-readiness/v1` 合同：证明本地/私测运维证据已闭环，同时明确列出 centralized logs/metrics/traces、alert routing、on-call ownership、managed incident system、real restore drill、centralized audit retention、managed database/queue cutover 等 P2 阻断项。私测 release / launch / health / acceptance 写入动作必须支持 receipt-first 响应和 read-model refresh routes，不得为了更新界面而在每次写入里强制嵌入完整 Manager Ready Package |
| **Agent 自主意图行** | A 端自主运行面必须把后端 strategy decision 投影为 `agent-autonomous-initiative/v1` 行。每行必须展示 Agent、选择的下一步动作、主动意图、判断理由、目标 artifact 类型、相关 review/evidence 目标、后端 run route，以及 proof/timeline/event ids。Product Team Operating Loop 与 Manager Flow Graph 必须消费同一组 initiative rows，让 Agent 的主观能动性可审计，而不是只停留在营销文案或前端解释里 |
| **Agent 间消息证明** | Agent-to-Agent message 不能只表现为群聊气泡或 Agent state 变化。`POST /projects/:id/agents/:agentId/message` 写入后，Manager Dashboard 必须展示 sender worklog、target inbox/obligation、direct receipt 和 transcript proof；Timeline/Event Ledger 必须记录 `agent-message` / `agent-to-agent-message` 证据；Manager Flow Graph 必须渲染 Agent communication node；Readiness Proof Map 必须暴露 `agentMessageRoutes` / `agentMessageSummary`，把 message id、transcript route、timeline log、event-ledger proof、sender/target Agent ids 和 delivery readiness 串起来。该合同用于证明 Agent 自主协作真的发生并被 C/B 端可追溯，而不是浏览器本地聊天模拟 |
| **协作意图队列** | Manager Ready Package 必须展示 `collaboration-intent-queue/v1`，后端必须通过 `GET /projects/:id/collaboration-intent-queue` 暴露同一份合同。该合同必须把 kickoff self-marketing、role negotiation、group-chat attention、Manager next action、Agent autonomous initiatives、review/revision/final closure 排成可审计队列，输出 queue position、actor、intent、rationale、runnable backend route、proof ids、timeline/event ids、backend routes 与 checksum。它必须进入 Manager Flow Graph 的 `collaboration-intent-queue` 节点，并在 Readiness Proof Map 暴露 `collaborationIntentQueueRoutes`。该队列用于回答“谁接下来想发言或行动、为什么、通过哪条后端路径执行”，不得被包装为生产级无人值守自治；managed queue/cron、durable audit、成本控制、客户验收阈值、事故恢复和 provider/BYOK 未闭环前必须保持 `readyForProduction: false` |
| **Reviewer 前端审核入口** | Manager Dashboard 中的 Agent submission 行必须允许 Reviewer 从 C 端提交 `POST /projects/:id/submissions/:submissionId/reviews`，记录 verdict、comments 和 requested changes；该动作必须写入群聊、timeline、event ledger、submission-review-workflow、Manager Flow Graph、Readiness Proof Map 和相关 Agent Dashboard，并通过轻量 receipt 刷新后端读模型，不得只在前端生成 review 状态。若后端写入失败，前端必须显示失败、保留 Reviewer 草稿，并把 pending receipt 替换为失败状态，不得把 `pending-backend-confirmation` 当成可追溯 review receipt |

- **运行健康与恢复可见性**：Manager Ready Package 必须展示本地运行健康、worker 队列、审计流顺序、持久化恢复源、数据库迁移 dry-run、证明链可回放、告警规则草案、恢复 runbook 和 `operations-incident-drill/v1` 演练收据；演练收据至少要证明告警能路由到 proof surface、恢复步骤有 evidence route、队列/持久化/审计链检查通过；该能力只能证明本地/内测可观测性，正式上线仍需要集中日志、指标、告警、备份恢复演练和事故责任机制
- **Managed Persistence Adapter 上线验证**：在替换本地 JSON/file store 前，Manager Ready Package 必须展示 managed persistence adapter plan 与 dry-run 结果；后端必须通过 `GET /projects/:id/persistence-adapter-plan` 和 `GET /projects/:id/persistence-adapter-dry-run` 暴露数据库 cutover 合同，至少覆盖项目、消息、事件账本、任务、Agent 状态、提交、证据搜索、评审、成员策略、签名重放记录、访问审计、安全审计流、provider usage ledger、provider eval runs、worker runs、read-model checkpoints 等关键表，并验证 adapter execution receipt、shadow-read parity、transaction rollback、backup/restore、RLS 草案、audit-stream 连续性和 read-model checkpoint parity；dry-run 通过只能证明可进入内测 cutover 演练，不等于已经完成真实托管数据库部署
- **Worker 恢复状态可见性**：Manager Ready Package 必须展示 worker execution receipt、retry state、dead-letter queue、最大重试次数和恢复 route；本地 MVP 可以用该合同证明队列恢复语义，但正式上线仍需要生产级 queue/cron、durable lease、managed dead-letter storage 和恢复演练
- **Queue Adapter 上线验证**：在替换本地 Node scheduler 前，Manager Ready Package 必须展示 worker-queue adapter plan 与 dry-run 结果，至少覆盖 adapter driver status、adapter execution receipt、enqueue、idempotency、lease acquisition、dispatch route、execution receipt ack、retry policy import、dead-letter recovery、queue inspection、`worker-queue-adapter-snapshot-parity/v1` 快照一致性和 cutover blocker；dry-run 通过只能证明可进入内测，不等于已部署真实生产队列
- **外部 Adapter Gateway 验证**：当部署方选择 `http-json` 私有 adapter gateway 时，必须先通过共享 gateway 合同验证。该验证至少包含 `adapter-gateway-health/v1`、`adapter-gateway-state-summary/v1`、`managed-persistence-adapter-execution-receipt/v1` 和 `worker-queue-adapter-execution-receipt/v1`。后端必须通过 `GET /projects/:id/adapter-gateway-preflight` 暴露 `adapter-gateway-preflight/v1`：本地 shadow 模式要证明当前私有试点 rehearsal 路径明确；`http-json` 模式要读取私有 gateway 的 live health、state summary、能力声明和存储/队列元信息，并把结果纳入 Manager Ready Package 与部署前预检。配置 `MANAGED_PERSISTENCE_ADAPTER_DRIVER=http-json` 或 `WORKER_QUEUE_ADAPTER_DRIVER=http-json` 后，对应项目级 dry-run API 必须能调用私有 gateway 并返回 gateway execution receipt。产品应提供一个本地私有 gateway 参考进程，支持 bearer token、storage adapter status、shadow table record 持久化、queue row / lease / dead-letter 状态持久化、persistence dry-run 和 queue dry-run，以便私有试点先完成部署形态验证；但在真实数据库/队列 cutover 审批前不得返回 `productionCutoverReady: true`
- **Postgres-compatible Gateway Store 验证**：当 `ADAPTER_GATEWAY_STORAGE_DRIVER=postgres` 或 `postgres-compatible` 时，gateway storage adapter 必须暴露 `adapter-gateway-postgres-schema-plan/v1`、脱敏后的数据库连接信息、schema 名称、query-bound 状态、最新写入执行摘要和 `adapter-gateway-postgres-readback/v1` 读回摘要；验证必须覆盖 schema plan、project summary、table record、queue row、queue lease、dry-run receipt、state snapshot 写入操作，以及 snapshot checksum 与 table/queue count readback parity。该验证只证明私有 gateway 已具备托管 Postgres 的 schema/upsert/readback 合同边界，不等于真实数据库备份恢复、RLS、监控和 cutover 审批已经完成。
- **本地数据存储**：所有项目数据、会议记录、AI 交互日志，均存储在用户部署环境，平台不收集任何数据

## 五、核心页面模块

### Production Launch Evidence Integrity Update

- `production-launch-audit/v1` must consume `production-evidence-integrity-audit/v1` as a first-class production gate named `managed-production-evidence-integrity`. Local/test receipts may verify control workflows, but they must keep this production gate failed until every required operations, deployment, security, and provider control points to explicit signed `managed-production` evidence.
- `production-launch-gap-register/v1` must also consume `production-evidence-integrity-audit/v1`. When signed managed-production evidence is missing, it must expose a routed `managed-production-evidence-integrity` gap pointing to `GET /projects/:id/production-evidence-integrity-audit`; when signed managed-production receipts cover all required controls, that specific gap must close without claiming broader public-production readiness unless all other launch controls are complete.
- `brainstorm-layer/v1` must expose a generic product-team brainstorm layer from `brainstorm-board` submissions. It must show visible alternatives, linked discovery/evidence/downstream artifacts, proof ids, timeline/event ids, Flow Graph route, Proof Map route, Manager Ready Package summary, and production no-go status. Research Project can validate this layer, but the contract must not contain paper-specific fields.
- Agent Dashboard must expose each Agent's personal brainstorm contribution when that Agent submits a `brainstorm-board`. It must show the Agent's alternative directions, proof ids, timeline/event ids, and route back to the Manager brainstorm layer so Agent initiative and "self-marketed" ideas remain visible in both individual and Manager views.
