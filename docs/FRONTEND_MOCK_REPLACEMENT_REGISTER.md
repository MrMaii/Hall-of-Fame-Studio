# Frontend Mock Replacement Register

This register tracks the work needed to turn Hall of Fame Studio from a frontend-heavy prototype into a backend-backed AI product-team platform.

## Source Labels

Every manager-facing surface should eventually fall into one of these states:

| Label | Meaning | Production rule |
| --- | --- | --- |
| `backend-backed` | The UI is rendering a backend read model or backend action receipt. | Allowed for private-pilot and production hardening. |
| `backend-required` | The backend is online, but the required read model is missing. | Show missing state; do not synthesize fake rows. |
| `frontend-fallback` | The UI generated local rows from project state. | Allowed only for offline mode or explicit demo/sample projects. |
| `sample-fixture` | The user intentionally loaded a demo project. | Must be visibly separated from real projects. |
| `validation-fallback` | Deterministic local/model fallback used by Harnesses. | Allowed in tests; must not be marketed as production capability. |

## Replacement Principles

- A backend-online real project must never silently use frontend-generated rows or browser-local runtime mutation for Manager governance, release readiness, proof maps, action queues, chat, meeting, assignment, change, or manual pulse success.
- Demo project generation can stay, but it must be labeled as sample data and must not become the normal project creation path.
- Each replacement should add or update Harness coverage: API shape, UI visibility, Flow Graph/Proof Map linkage, and no production overclaim.
- If the backend model is missing, the UI should show `backend model missing` rather than pretending the data exists.
- User-facing failure copy for backend-online real projects should say browser-local fallback was suppressed or a draft was restored; it should not describe the suppressed path as a local mock result.
- Mutating backend routes may return lightweight action receipts when the caller sends `includeReadModels: false`. The UI must then refresh Manager Dashboard, Manager Ready Package, Manager Flow Graph, or Agent Dashboard from their standalone backend routes instead of filling the gap with frontend rows.
- Agent Market roster changes are backend writes for backend-managed projects. Contracting an Agent into a real project must call `POST /projects/:id/agents/contract` and refresh backend proof routes; if the saved backend target is missing or the route fails, React must block the local roster mutation instead of showing a browser-only team change.
- Manager direct commands are backend collaboration writes for backend-managed projects. Dual-channel change broadcasts, Manager change intake, and Leader assignment must use the backend project command routes; if the saved backend target is missing, React must restore/block the command instead of creating local chat, meeting, or change proof.
- Legacy War Room controls follow the same boundary. Starting a meeting, sending terminal directives, or closing a meeting for a backend-managed project must use backend meeting routes; without a saved backend target, React must keep the draft/session visible and block local Agent-session simulation, local change proof, or local close logs.
- Flow Graph and dashboard proof navigation must use backend-aware proof openers. Buttons that focus transcript or timeline proof for backend-managed projects must call the shared chat/timeline proof helpers, which sync backend transcripts, timeline, and events first; they must not set browser focus ids directly from local change, handoff, task, or Flow Graph rows.
- Backend transcript search results follow the same rule: clicking a search hit must open chat proof through the shared backend-aware proof helper instead of directly focusing a browser message id.
- Settings API key/search endpoint fields are draft-enabled after a saved backend target; `Seal` persistence stays locked until the Secret Vault is ready. Draft values are transient React state and never durable browser settings; search endpoint/key configuration becomes durable only through backend Secret Vault receipts. Use `npm run agents:server:validate` to prove `npm run agents:server` can start with `SECRET_VAULT_ENABLED=true` / `SECRET_VAULT_KEY`, seal a key through `/secret-vault/seal`, return safe `/secret-vault/records` metadata, bind the running provider status to `apiKeySource: local-secret-vault`, set `runtimeEnabled: true`, restart, and rehydrate from `SECRET_VAULT_RECORDS_FILE`. Use `npm run agents:search-provider:vault-endpoint` to prove `search.endpoint` plus `search.apiKey` can be sealed through the backend, make `/search/test` call a local gateway, and rehydrate after restart. Use `npm run ui:settings-agents-server` when the replacement touches Settings or backend startup; it opens the real UI against the real `agents:server` process, syncs/selects a backend project, and verifies Keys, Health, Deployment, Models, Integrations, and Workspace against backend proof routes before treating Settings as backend-backed.
