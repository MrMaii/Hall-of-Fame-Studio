# Frontend Mock Replacement Register

This register tracks the work needed to turn Hall of Fame Studio from a frontend-heavy prototype into a backend-backed AI product-team platform.

## Source Labels

Every manager-facing surface should eventually fall into one of these states:

| Label | Meaning | Production rule |
| --- | --- | --- |
| `backend-backed` | The UI is rendering a backend read model or backend action receipt. | Allowed for private-pilot and production hardening. |
| `backend-required` | The backend is online, but the required read model is missing. | Show missing state; do not synthesize fake rows. |
| `frontend-fallback` | The UI generated local rows from project state. | Allowed only for offline mode or explicit demo/sample projects. |
| `sample-fixture` | The user intentionally loaded a demo project. | Must be visibly separated from real projects. |
| `validation-fallback` | Deterministic local/model fallback used by Harnesses. | Allowed in tests; must not be marketed as production capability. |

## Replacement Principles

- A backend-online real project must never silently use frontend-generated rows or browser-local runtime mutation for Manager governance, release readiness, proof maps, action queues, chat, meeting, assignment, change, or manual pulse success.
- Demo project generation can stay, but it must be labeled as sample data and must not become the normal project creation path.
- Each replacement should add or update Harness coverage: API shape, UI visibility, Flow Graph/Proof Map linkage, and no production overclaim.
- If the backend model is missing, the UI should show `backend model missing` rather than pretending the data exists.
- Mutating backend routes may return lightweight action receipts when the caller sends `includeReadModels: false`. The UI must then refresh Manager Dashboard, Manager Ready Package, Manager Flow Graph, or Agent Dashboard from their standalone backend routes instead of filling the gap with frontend rows.
- Settings API key entry is usable only through a running backend Secret Vault. Search endpoint/key configuration is usable only through backend Secret Vault receipts. Use `npm run agents:server:validate` to prove `npm run agents:server` can start with `SECRET_VAULT_ENABLED=true` / `SECRET_VAULT_KEY`, seal a key through `/secret-vault/seal`, return safe `/secret-vault/records` metadata, bind the running provider status to `apiKeySource: local-secret-vault`, set `runtimeEnabled: true`, restart, and rehydrate from `SECRET_VAULT_RECORDS_FILE`. Use `npm run agents:search-provider:vault-endpoint` to prove `search.endpoint` plus `search.apiKey` can be sealed through the backend, make `/search/test` call a local gateway, and rehydrate after restart. Use `npm run ui:settings-agents-server` when the replacement touches Settings or backend startup; it opens the real UI against the real `agents:server` process before treating the Settings Keys tab as backend-backed.
- Local MVP startup readiness is now a backend route consumed by Settings instead of a frontend inference. `GET /local-mvp-startup-readiness` returns `local-mvp-startup-readiness/v1` with Secret Vault, model/search runtime, provider-vault redaction, project catalog, next action, validation command, and production-blocker rows; React renders the route/status/next action in `settings-secret-vault-local-startup-contract`, Manager Ready Package embeds `localMvpStartupReadiness`, Readiness Proof Map exposes `localMvpStartupReadinessRoutes`, and `npm run agents:local-mvp-startup-readiness` verifies blocked and Vault-ready states without launching a browser.
- Settings Health Quick Check is now a backend route instead of browser-synthesized diagnostic rows. `GET /settings/health-readiness` returns `settings-health-readiness/v1` with backend API, startup readiness, Secret Vault, model/search provider status, explicit test routes, worker status route, project catalog, validation commands, and production blockers; the Health tab renders those rows, Manager Ready Package embeds `settingsHealthReadiness`, Readiness Proof Map exposes `settingsHealthReadinessRoutes`, while Workflow Smoke remains the explicit deeper probe path. - Use `docs/LAUNCH_READINESS_GATES.md` plus `npm run launch:gates` as the launch-tier source of truth while replacing mocks. A replacement can support P0 local backend MVP, P1 customer private pilot, or P2 public production only when the corresponding gate in that document is satisfied; local/private-pilot receipts must not be described as public-production evidence.
