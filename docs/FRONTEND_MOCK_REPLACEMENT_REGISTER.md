# Frontend Mock Replacement Register

This register tracks the work needed to turn Hall of Fame Studio from a frontend-heavy prototype into a backend-backed AI product-team platform.

## Source Labels

Every manager-facing surface should eventually fall into one of these states:

| Label | Meaning | Production rule |
| --- | --- | --- |
| `backend-backed` | The UI is rendering a backend read model or backend action receipt. | Allowed for private-pilot and production hardening. |
| `backend-required` | The backend is online, but the required read model is missing. | Show missing state; do not synthesize fake rows. |
| `frontend-fallback` | The UI generated local rows from project state. | Allowed only for offline mode or explicit demo/sample projects. |
| `sample-fixture` | The user intentionally loaded a demo project. | Must be visibly separated from real projects. |
| `validation-fallback` | Deterministic local/model fallback used by Harnesses. | Allowed in tests; must not be marketed as production capability. |

## Replacement Principles

- A backend-online real project must never silently use frontend-generated rows or browser-local runtime mutation for Manager governance, release readiness, proof maps, action queues, chat, meeting, assignment, change, or manual pulse success.
- Demo project generation can stay, but it must be labeled as sample data and must not become the normal project creation path.
- Each replacement should add or update Harness coverage: API shape, UI visibility, Flow Graph/Proof Map linkage, and no production overclaim.
- If the backend model is missing, the UI should show `backend model missing` rather than pretending the data exists.
- Mutating backend routes may return lightweight action receipts when the caller sends `includeReadModels: false`. The UI must then refresh Manager Dashboard, Manager Ready Package, Manager Flow Graph, or Agent Dashboard from their standalone backend routes instead of filling the gap with frontend rows.
- Use `npm run agents:product-team:core` as the fast backend C/A loop regression gate while replacing mocks. It stops after the backend has proven kickoff, self-marketing, evidence, brainstorm, submissions, generated drafts, review/revision/final delivery, Flow Graph, Proof Map, Agent Dashboard, transcript, timeline, and event proof. Use `npm run agents:product-team:research-sample` when the replacement touches Research-sample positioning or Product Team Delivery Trace display; it proves the same backend/HTTP trace with generic product-team stages and rejects paper/thesis/manuscript-specific protocol drift. Use `npm run agents:product-team:cycle-consistency` when a replacement touches Autonomous Run Control, Worker Queue, Flow Graph, Proof Map, or Ready Package autonomy continuity; it proves the signed three-step consistency route without running the full launch-hardening chain. Use `npm run agents:product-team:private-pilot:launch-handoff` when a browser test needs the generic product-team project prepared right before C-side launch approval and evidence handoff clicks; use `npm run agents:product-team:private-pilot:handoff` only when a test starts after launch approvals and evidence-export download audit are already recorded. Use the staged private-pilot gates (`npm run agents:product-team:private-pilot:release`, `:launch`, `:health`, `:acceptance`, `:ops-readiness`) when a replacement only needs proof through one customer-visible launch or post-acceptance operations-readiness receipt. Use `npm run agents:product-team:private-pilot` when a replacement must prove the full customer-visible private-pilot handoff through launch approvals, evidence archive/export, release candidate, launch run, health check, and acceptance report without running public-production hardening receipts. Use `npm run ui:manager-backend:core` as the fast browser C/A control-loop gate for Backend Worker Station sample adoption, Autonomous Run Control, direct Agent Autonomous Queue receipts, and Autopilot scheduler receipts. Use `npm run ui:manager-private-pilot` when the replacement must prove C-side launch approvals, evidence export request/approval/download audit, Ready Package receipt clicks, and Flow Graph/Proof Map evidence all land as A-side backend receipts. Use `npm run agents:product-team` and `npm run ui:manager-backend` for the longer release-hardening gates.
- Use `docs/LAUNCH_READINESS_GATES.md` plus `npm run launch:gates` as the launch-tier source of truth while replacing mocks. A replacement can support P0 local backend MVP, P1 customer private pilot, or P2 public production only when the corresponding gate in that document is satisfied; local/private-pilot receipts must not be described as public-production evidence.

## First Implemented Gate

`src/App.jsx` now defines a Manager fallback gate:

- offline or explicit Manager Demo projects may use frontend fallback rows
- backend-online real projects receive `backend-model-missing` read models instead of synthesized rows
- the Manager Live Command Center and Manager Flow Graph display `backend-backed`, `demo data`, or `backend model missing`
- Manager Scenario Walkthrough, Manager Action Playbook, Manager Use Case Audit, and Sync Protocol Audit now expose the same source labels, so C-side governance controls cannot visually blur backend read models with offline/demo fallback rows
- project initiation approval now fails closed when the backend approval command fails; local project creation is only available through an explicit development fallback flag
- kickoff meeting sessions now expose `kickoff-generation-provenance/v1`, so deterministic validation, model-provider rehearsal, provider-backed model generation, and development fallback are visibly separated; approval persists the same provenance into project initiation, kickoff charter evidence, and Manager Dashboard, and the real-project browser Harness requires the approved Dashboard card to keep production claims blocked
- Agent evidence-search, submission, and artifact-draft write routes now support `includeReadModels: false`, returning a backend action receipt with deferred read-model routes. The product-team acceptance Harness verifies this so frontend replacement can submit work quickly and refresh authoritative backend projections afterward.
- Agent submissions now carry `agent-artifact-storage-proof/v1` from the backend artifact pipeline. Manager Dashboard rows, Flow Graph submission attachments, Proof Map routes, Artifact Quality Audit, Project Evidence Archive, and persistence snapshot rows all preserve the same proof checksum, so frontend replacement can treat missing storage proof as a backend gap instead of filling a fake artifact node locally.
- Manager write commands now try the configured backend endpoint even when the local station status display is stale. Once a project has backend sync evidence from the catalog, project snapshot, or Manager Dashboard, a real command failure stays fail-closed instead of falling back locally; only offline-only projects, sample fixtures, or explicit development fallback can use browser-local mutation. This keeps C-side chat, meeting, change intake, Leader assignment, Manager Flow Graph confirmation, marketplace Agent contract, and manual pulse controls from silently becoming browser-local after an unrelated read-model sync issue. `npm run ui:manager-backend` now verifies a custom dual-channel Manager change persists to the backend with source messages, owner plan, team sync, and immediate owner work-pulse evidence.
- The React Agent Focus Workspace now includes an Agent Workbench that uses those backend routes for evidence, typed artifact submissions, and generated draft submissions. It stores the lightweight receipt and refreshes Manager Dashboard, Manager Ready Package, Manager Flow Graph, and Agent Dashboard from standalone backend read routes instead of synthesizing local rows. Revision and final-deliverable submissions can link `respondsToReviewId`, `revisesSubmissionId`, and final `supersedesSubmissionIds` from the UI instead of requiring a direct API call.
- Agent Focus now separates browser project snapshot context from the backend Agent Dashboard. Backend-online real projects show a source tag (`backend-backed` or `backend-required`) and a `Sync Agent Dashboard` missing state when `/agents/:agentId/dashboard` has not been returned, so the Agent's local inbox/worklog snapshot is not treated as the personal backend read model.
- The React Manager Dashboard now includes a Reviewer review composer on Agent submission rows. It posts to `POST /projects/:id/submissions/:submissionId/reviews` with `includeReadModels: false`, stores the backend review receipt, and refreshes Manager Dashboard, Manager Ready Package, Manager Flow Graph, Timeline/Event, and Agent Dashboard read models instead of inventing frontend review state.
- The Marketplace contract flow now posts to `POST /projects/:id/agents/contract` for backend-online real projects. The backend persists an `agent-contract/v1` roster record, team member, Agent worklog proof, timeline/event proof, and Manager Flow Graph collaboration node, while React refreshes Manager/Agent read models instead of adding a local-only recruited Agent row.
- Per-Agent worker cycles can now create real submission, evidence-search, review, and revision-response nodes when explicitly requested. `submitWorkArtifact: true` on `POST /projects/:id/agents/:agentId/work-cycle`, and `submitAgentWorkArtifacts: true` on HTTP scheduler ticks, turns completed autonomous work into a standard Agent submission with task, chat, timeline, event, Agent Dashboard, and Flow Graph proof. `workArtifactType: "auto"` and scheduler submissions infer generic product-team artifact types such as `brainstorm-board` and `evidence-packet` from task intent instead of always emitting `progress-brief`; evidence-oriented tasks also record a standard `evidence-search` row and link it into the submitted packet. `reviewPendingSubmission: true` / `reviewPendingSubmissions: true` lets Reviewer workers process assigned pending submissions through the standard submission-review contract. `respondToReviewObligation: true` / `respondToReviewObligations: true` lets the Submitter worker answer `changes-requested` obligations with linked `revision-note` or `final-deliverable` submissions. `npm run agents:scenario` now verifies an isolated HTTP scheduler chain from evidence-packet to requested changes, linked revision, accepted revision, accepted final deliverable, Manager Flow Graph closure, and Readiness Proof Map routes. This keeps autonomous output, search/evidence, review, revision closure, and final delivery on the backend contract while leaving production volume/review policy controls as a launch blocker.
- Autonomous worker evidence searches now use the same auditable evidence custody shape as provider-backed searches: `agent-autonomous-worker` provider receipt, checksummed source snapshots, internal proof-route source safety, source-review readiness, evidence custody rows, archive contents, and persistence rows. `npm run agents:product-team` now verifies that scheduler-produced evidence can grow beyond the original 3-source/1-receipt fixture while every provider-backed evidence row still has snapshots and receipts.
