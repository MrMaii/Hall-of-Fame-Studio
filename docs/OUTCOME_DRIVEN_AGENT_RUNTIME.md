# 结果驱动的 Agent 运行协议

这套协议解决一个具体问题：Agent 系统可能产生大量聊天、监督、确认、审计记录和流程节点，但没有形成可验收的项目成果。运行时现在把“有活动”与“有进展”分开计算。

## 根因

旧运行方式存在六类结构性问题：

1. **度量替代**：消息数、心跳、回执和任务脉冲被当作进展。
2. **协调优先级倒置**：管理确认持续抢占真正的检索、写作、编码或检查任务。
3. **执行器缺失**：角色和流程很丰富，但任务没有绑定必须实际调用的工具与证据形状。
4. **失败伪装**：搜索或模型不可用时，模板和本地证明仍可能被包装成工作成果。
5. **审查不独立**：同一 Agent 可能既生产又验收，可信度指标因此变成自我证明。
6. **无产出循环没有熔断**：系统可以无限客套，而不会进入明确的停滞状态。

## 统一执行闭环

每项工作都遵循同一条链路：

`WorkContract → 前置条件检查 → 专业执行器 → 实质产物门禁 → 独立审查 → 进度 → 可追踪交接`

`WorkContract` 至少包含所有者、独立审查者、工作类型、必需工具、必需证据和验收标准。开放任务始终优先于非阻塞性的管理消息。协调只有在解除具体交付阻塞时才允许运行，而且协调本身永远不增加进度。

## 各类项目的实质门禁

| 工作类型 | 必须出现的产物与证明 |
| --- | --- |
| 研究 | 至少 3 个 provider 来源、包含来源引用的实质报告、独立接受；弱证据只能形成证据缺口，不能形成结论 |
| 技术交付 | 实际变更、测试或验证证明、独立接受 |
| 创意/设计 | 至少 2 个真实方案及选择理由、评估证明、独立接受 |
| 运维 | 检查结果、实际变更、变更后验证、独立接受 |
| 通用工作 | 与任务内容直接相关的非模板产物、独立接受 |

系统会拒绝固定模板、纯协调文本、自我验收、没有外部来源的研究结论，以及没有工具证明的技术或运维“完成”。

## 失败与健康语义

- 搜索、模型或专业工具不可用时，任务保持未完成，并公开具体 blocker。
- provider 仅“已配置”不等于可用；最近的真实传输失败会使 provider readiness 失败。
- 连续两个执行周期没有实质增量时，任务进入 `STALLED_NO_MATERIAL_DELTA`，停止礼貌循环。
- 项目进度只由已接受的实质交付物贡献。历史基线保留，但新消息、回执和心跳不会再加分。
- 工作区投影写入失败不会丢失已写入内部内容寻址存储的产物；运行时会返回明确的 `workspaceProjection` blocker。

## 交接协议

实质交接使用 `material-handoff/v1`，包含 artifact id、版本、checksum、证据 id、开放问题、下一所有者和审查信息。群聊、流程图和审计账本只投影这份真实交接，不另外制造一份“看起来完成”的状态。

## 验证与运行

```powershell
npm run agents:outcome-runtime
npm test
npm run build
```

运行时操作员应同时检查 scheduler、provider 和 material-output 三个 readiness gate。只要任一必需 gate 失败，就应修复 blocker，而不是通过增加会议、消息或可信度打分来补偿。
